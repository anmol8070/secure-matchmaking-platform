# Phase 12 — Private Video Calls (WebRTC)

Private one-to-one video calls between **accepted connections**. Media goes
directly between the two browsers with WebRTC, relayed by TURN when a
direct path is impossible. The API only authorizes calls, relays signalling
and stores **call metadata**. Nothing is recorded: no audio, video,
screenshots, SDP or ICE data is stored or logged.

## 1. Architecture

```
 Browser A                      API server (Express + Socket.IO)                 Browser B
 ─────────                      ────────────────────────────────                 ─────────
 getUserMedia ──▶ call:initiate ─▶ authorize (Phase 10 rules) ─▶ video_calls row ─▶ call:incoming (all B devices)
                                                                     ◀── call:accept (after B's camera/mic is ready)
 RTCPeerConnection ── call:offer ─▶ authorize + validate ─▶ relay in call:<id> room ─▶ RTCPeerConnection
                  ◀── call:answer ◀──────────────────────────────────────────────────
                  ◀─▶ call:ice-candidate (both ways, same checks)
 ════════════════════ audio/video: peer-to-peer (or via TURN) — never through the API ════════════════════
 connectionState=connected ─▶ call:connected ─▶ status "connected"
 End call ─▶ call:end ─▶ status "ended" + duration ─▶ call:ended to both users
```

* **Rooms.** `user:<id>` holds all devices of a user and is used for ringing
  and state updates. `call:<id>` holds only the two devices in the call: the
  caller's device that placed it and the receiver's device that accepted it.
  SDP and ICE are relayed only inside `call:<id>`. A client can never name a
  room or a socket id; anything extra in a payload (e.g. `targetSocketId`)
  is stripped.
* **Roles.** The caller sends every offer, including ICE restarts. The
  receiver answers. The server enforces this.

## 2. Call lifecycle and states

```
ringing ──accept (receiver)──▶ accepted ──a peer reports "connected"──▶ connected ──end──▶ ended
   │                              │                                         └──failure──▶ failed
   ├──reject (receiver)──▶ rejected└──end / failure / connect timeout──▶ ended | failed
   ├──caller ends──▶ cancelled
   └──no answer within CALL_RING_TIMEOUT_SECONDS──▶ missed
busy — the receiver was already in a call (recorded, never rings)
```

* Call ids are generated by the server, and every state change is a
  conditional `UPDATE … WHERE status IN (allowed)`. A rejected call can never
  become active, and a finished call accepts no more signalling (409).
  Repeated events, double clicks, two devices or reconnects change nothing
  twice, so a missed call is recorded once.
* A call is **connected** only when a browser's `RTCPeerConnection` reaches
  `connected`. Successful signalling alone does not count.
* One active call per user. Both users' rows are locked while placing a
  call, so two simultaneous calls cannot both ring. A second call to someone
  in a call gets **busy**. A caller who is already in a call gets 409.
* Timers: ringing → missed (`CALL_RING_TIMEOUT_SECONDS`, default 30) and
  accepted but never connected → failed (`CALL_CONNECT_TIMEOUT_SECONDS`, 45).
  A participant may be away for up to `CALL_REJOIN_GRACE_SECONDS` (20), e.g.
  after a refresh or a network drop. They re-join with `call:join` and the
  peers renegotiate. If they don't return, the call ends as
  `failed / participant_left`. A sweep every 15 s closes calls whose timers
  were lost (server restart, other instance).

## 3. Who may call

Calls use the Phase 10 rule `connectionService.canUsersCommunicate` and the
block check. The pair must have an **accepted** connection, **no block** in
either direction, and both accounts **active**. Pending, rejected,
cancelled and disconnected relationships are refused with 403. The rule is
re-checked:

* when placing and when accepting a call;
* on signalling: at most every 5 s per call (cached), plus immediately by
  events. **Blocking a user or removing the connection ends their call at
  once** (`endReason: unavailable / disconnected`).

| Action | Who |
| --- | --- |
| Place a call | Either member of an allowed pair |
| Accept / reject | The receiver only (the caller gets 403) |
| Offer | The caller's bound device |
| Answer | The receiver's bound device |
| ICE candidates, connected, failed, end | Either participant (signalling from the bound device only) |
| View a call / history | Participants only (everyone else gets 404) |

## 4. REST API (`/api/v1/calls`, Bearer token)

| Method & path | Purpose |
| --- | --- |
| `GET /calls/ice-servers` | STUN/TURN servers for `RTCPeerConnection` (`Cache-Control: no-store`) |
| `GET /calls/history?limit=20&before=<callId>` | My calls, newest first (cursor pagination) |
| `POST /calls` `{ receiverId }` | Place a call (same rules as `call:initiate`) |
| `GET /calls/:id` | One of my calls |
| `POST /calls/:id/accept` · `/reject` · `/end` | Call control (same rules as the socket events) |

REST and sockets share `callService`, so they enforce identical rules. The
browser uses the socket for call control, because accepting over the socket
also binds that device to the call. **Signalling (offer/answer/ICE) is
Socket.IO only.** A REST client that accepts a call must bind a socket with
`call:join` before it can signal.

```json
{ "id": 41, "callerId": 7, "receiverId": 12, "direction": "outgoing", "status": "ended",
  "createdAt": "2026-10-22T10:00:00.000Z", "answeredAt": "2026-10-22T10:00:04.000Z",
  "connectedAt": "2026-10-22T10:00:06.000Z", "endedAt": "2026-10-22T10:05:06.000Z",
  "durationSeconds": 300, "endReason": "hangup",
  "otherUser": { "userId": 12, "name": "Riya Shah", "profilePicture": null, "age": 29, "location": "Pune" } }
```

Errors: 400 calling yourself · 401 no/invalid token · 403 not connected
(`Video calls are available only between connected users.`), blocked
(`You cannot call this user.`) or wrong role · 404 unknown call or not a
participant · 409 already in a call / invalid state transition / already
ended · 422 malformed ids or payloads · 429 too many calls or signalling
messages.

## 5. Socket.IO events

Client → server (each one takes an acknowledgement callback that receives
`{ success, ... }` or `{ success: false, error, code }`):

| Event | Payload | Ack |
| --- | --- | --- |
| `call:initiate` | `{ userId }` | `{ call, busy, receiverOnline }` |
| `call:accept` | `{ callId }` | `{ call }` (binds this device) |
| `call:reject` | `{ callId }` | `{ call }` |
| `call:join` | `{ callId }` | `{ call }`: re-binds a device after a refresh or reconnect |
| `call:offer` | `{ callId, description: { type: 'offer', sdp } }` | `{}` |
| `call:answer` | `{ callId, description: { type: 'answer', sdp } }` | `{}` |
| `call:ice-candidate` | `{ callId, candidate: { candidate, sdpMid, sdpMLineIndex, usernameFragment } }` | `{}` |
| `call:connected` | `{ callId }` | `{ call }` |
| `call:failed` | `{ callId, reason? }` | `{ call }` |
| `call:end` | `{ callId, reason?: 'hangup' \| 'navigated_away' }` | `{ call }` |

Server → client:

| Event | To | Payload |
| --- | --- | --- |
| `call:incoming` | receiver's devices | `{ call, caller }` (public card only) |
| `call:busy` | caller's devices | `{ call }` |
| `call:accepted` · `call:connected` · `call:ended` | both users' devices | `{ call }` (metadata only) |
| `call:offer` · `call:answer` · `call:ice-candidate` | the other bound device | `{ callId, fromUserId, description \| candidate }` |
| `call:peer-left` · `call:peer-rejoined` | the call room | `{ callId, userId }` |

Limits: an SDP may be up to 48 KB and a candidate up to 2 KB, within a
64 KB socket frame. `CALL_SIGNAL_RATE_LIMIT` (300) signalling messages per
user per 10 s; `CALL_INITIATE_RATE_LIMIT` (10) calls per user per minute.

## 6. Database: `video_calls`

| Column | Notes |
| --- | --- |
| `call_id` | PK |
| `caller_id`, `receiver_id` | FK → users (RESTRICT), CHECK not equal |
| `status` | CHECK `ringing, accepted, connected, rejected, missed, cancelled, busy, ended, failed` |
| `created_at` | When the call was placed |
| `answered_at`, `connected_at`, `ended_at` | Lifecycle timestamps |
| `duration_seconds` | Connected time only |
| `end_reason` | `hangup`, `rejected`, `cancelled`, `no_answer`, `busy`, `connect_timeout`, `connection_failed`, `participant_left`, `unavailable`, `disconnected`, `not_allowed`, `navigated_away` |
| `ended_by` | FK → users (SET NULL) |
| `updated_at` | Maintained by the database |

Indexes: `(caller_id, call_id)`, `(receiver_id, call_id)` for history, and
`(status, created_at)` for active-call lookups and the sweep. No media or
signalling data is stored.

## 7. STUN / TURN

```
WEBRTC_STUN_URL=stun:stun.l.google.com:19302      # comma-separated; development default
WEBRTC_TURN_URL=turn:turn.example.com:3478?transport=udp,turns:turn.example.com:5349
WEBRTC_TURN_SECRET=<coturn static-auth-secret>    # preferred
WEBRTC_TURN_TTL_SECONDS=3600
# or, for simple setups only:
WEBRTC_TURN_USERNAME=  WEBRTC_TURN_CREDENTIAL=
```

* **STUN alone does not work on every network.** Symmetric NAT, corporate
  firewalls and many mobile networks need a **TURN relay**. Without one,
  some calls stay at "Connecting…" and end as `failed / connect_timeout`.
* With `WEBRTC_TURN_SECRET`, credentials are minted per user and per request
  using the standard "TURN REST API" scheme. coturn calls this
  `use-auth-secret` / `static-auth-secret`. The username is
  `<expiry>:<userId>` and the credential is
  `base64(HMAC-SHA1(secret, username))`, valid for `WEBRTC_TURN_TTL_SECONDS`.
  The secret never leaves the server. Credentials are returned only by
  `GET /calls/ice-servers` (no-store) and are never logged.
* Static credentials work too but never expire. Avoid them in production.
* Production TURN: coturn (or a hosted TURN service) on a public IP. Open
  3478/udp+tcp and 5349/tcp (TLS) plus the relay port range (e.g.
  49152–65535/udp). Offer `turns:` on 443 for very restrictive networks.
* Never commit secrets: keep them in the environment or your secrets manager.

## 8. HTTPS and browsers

Browsers only allow camera and microphone access on **secure contexts**:
HTTPS, or `http://localhost` for development. In production, serve the
frontend over **HTTPS**, and the API and Socket.IO over **HTTPS/WSS** (TLS
at the load balancer is fine; enable WebSocket upgrades). If several API
instances run, set `REDIS_URL` so signalling reaches the other participant
on any instance (Phase 11 Redis adapter).

Media errors shown to the user, with "Try again" where it helps:
permission denied, no camera, no microphone, device in use, insecure page,
unsupported browser, generic failure.

## 9. Privacy

* No recording: no audio, video or screenshots are captured or stored.
* SDP and ICE data are relayed in memory only, never stored and never
  logged. Logs contain call ids, statuses and reasons only.
* TURN secret and credentials are never logged or returned except to the
  requesting user.
* Admins have no access to signalling. Call history is visible to its
  participants only.
* Existing account, connection and block rules apply on every call action.

## 10. Notifications

There is no notification system yet. The incoming call rings through the
open app (`call:incoming`, shown by `IncomingCall` on every page).
**A closed app or tab does not ring**: that needs push notifications,
which are not implemented. `callEvents` (`call.ringing`, `call.ended` with
status `missed`, …) is the hook for adding them later.

### Manual test on two devices

1. Run the backend and frontend. Use HTTPS, or `localhost` on both browsers.
2. Sign in as user A in one browser and as user B in another browser or an
   incognito window. A and B must be accepted connections.
3. A opens the chat with B and clicks **Video call**, then allows the camera
   and microphone.
4. B sees the incoming dialog and clicks **Accept**, then allows the camera
   and microphone. Both see "Connected" and each other's video.
5. Try **Mute** / **Camera off**: the other side loses audio/video while the
   call stays connected.
6. Refresh B's tab. Both show "Reconnecting…" and are back within seconds.
7. Click **End call**. Both see "Call ended", and the camera light turns off.
8. Repeat with **Reject**, with no answer (wait 30 s → "No answer"), and
   while B is in another call (busy). Then block B from A during a call: the
   call ends immediately.

## 12. Known limitations

* No push notifications: incoming calls ring only while the app is open.
* One-to-one calls only. No group calls, screen sharing or recording.
* Reaching "connected" is reported by the browsers. The server cannot
  observe the peer-to-peer media path itself.
* Without TURN some networks cannot connect. Production needs a TURN relay.
* Timers are per process; the 15 s sweep covers restarts and other
  instances, so a timeout may fire up to about 20 s late after a restart.
